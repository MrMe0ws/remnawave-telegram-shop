Актуальная связка этого форка:

| Remnawave | Бот |
|-----------|-----|
| **3.3.\* – 3.4.\*** | **5.x** |

| Remnawave     | Бот    |
| ------------- | ------ |
| 1.6           | 2.3.6  |

Для новых установок ориентируйтесь на Remnawave **3.4.\*** и бот **5.x**.

## Remnawave 3.4.0

Обновление панели с `3.3.*` до `3.4.*` **не требует изменений в боте**. Ломающая правка
API в `3.4.0` — одна: в объекте хоста `excludedInternalSquads` заменён на `internalSquads`
(с полями `mode` и `squads`), то есть модель доступа сменилась с исключающей на включающую.
Бот не обращается к `/api/hosts` ни из Go, ни из кабинета, поэтому правка его не задевает.

Теги, добавленные в `3.4.0` профилям, шаблонам, плагинам и сквадам, — это новые поля в
ответах панели. Клиент панели декодирует ответы обычным `json.Unmarshal`
(`internal/remnawave/client.go`), незнакомые поля игнорируются, так что `/api/internal-squads`
читается по-прежнему.

### Проверено на живой 3.4.0

Обновление стенда `3.3.2` → `3.4.0` прогнано целиком, контрактный набор
(`internal/remnawave/contract_test.go`, `contract_merge_test.go`) отработал **без единого
падения**: покупка по тарифу и продление, оживление заблокированного клиента, курсорная
пагинация на 300 пользователях, HWID, смена лимита устройств, списание дней, merge аккаунтов.

Сверх прогона сделан полный диф OpenAPI-спек `3.3.2` → `3.4.0` (обе с
`https://cdn.docs.rw/docs/openapi.json`) по тем эндпоинтам, которые бот реально вызывает:
**ни один не удалён и не сменил метод**, добавлен один — `/api/internal-squads/tags`,
который бот не зовёт. У схем, которые бот декодирует (`User`, `CreateUserBodyDto`,
`UpdateUserBodyDto`, internal squads, HWID), **не удалено и не добавлено ни одного поля** —
только три новых DTO под теги. Это закрывает вопрос о недокументированных правках:
форумный changelog — конспект, а диф спек полон.

Замеры на 3.4.0, важные для бота:

- **Миграция хостов ничего не ломает.** Панель конвертирует старые правила в
  `"internalSquads": {"mode": "EXCLUDE", "squads": []}` — «не исключаем никого», то есть
  доступ у всех сквадов ровно как до обновления. Сужения доступа при апгрейде не происходит.
  Риск появляется только если хост потом вручную перевести в режим `INCLUDE` с неполным
  списком сквадов: тогда клиенты на непопавших сквадах потеряют серверы молча, без ошибок
  в логах бота.
- **`username` в PATCH `/api/users` по-прежнему игнорируется** — допущение, на котором
  держится merge аккаунтов кабинета (опора на `remnawave_user_id`, а не на переименование),
  в 3.4.0 остаётся верным.
- **Панель по-прежнему допускает несколько профилей с одним `telegramId`** — порядок
  «сначала удалить проигравшего, потом патчить победителя» в merge обязателен и на 3.4.0.

## Почему 4.x и 5.x несовместимы

Remnawave **3.0.0** сменил идентификатор пользователя панели: поле `uuid` удалено,
пользователь адресуется числовым `id`. Заодно исчез эндпоинт `GET /api/users/by-telegram-id/{id}`,
на котором держался поиск клиента.

Из этого следует жёсткое правило:

- бот **4.x** против панели **3.x** не работает — у него нет ни одного живого способа найти пользователя;
- бот **5.x** против панели **2.8** не работает — он обращается к эндпоинтам, которых там ещё нет.

Промежуточного режима, понимающего обе версии, нет: обновлять панель и бота нужно вместе.
Ветка 4.x заморожена и остаётся для тех, кто пока сидит на 2.8.
