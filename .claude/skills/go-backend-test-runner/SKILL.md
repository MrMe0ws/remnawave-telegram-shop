# Запуск и анализ Go-тестов

Как визуальная проверка важна для фронтенда, тесты важны для бэка.
Падающие тесты означают баги перед деплоем.

## Когда применять

- Любая правка Go-кода в `cmd/`, `internal/`, `pkg/`.
- Перед git push, если в коммитах есть `*.go`.
- Не нужно для правок фронтенда, БД, конфигов (если только в `internal/config`).

## Порядок

### 1. Запустить тесты

```bash
# Все тесты со стандартным таймаутом
go test ./...

# С таймаутом подольше (для интеграционных тестов, если есть)
go test -timeout 30s ./...

# Конкретный пакет
go test ./internal/payment

# Конкретный тест
go test ./internal/payment -run TestYookasaWebhook
```

Смотреть в выводе:
- Какие тесты упали (FAIL)
- Какие прошли (ok)
- Таймауты (тест зависел от сети или был бесконечным)
- Паники (шум в stderr перед FAIL)

### 2. Анализ покрытия

```bash
# Сгенерировать профиль покрытия
go test -coverprofile=coverage.out ./...

# Вывести в консоль по пакетам
go tool cover -func=coverage.out

# Открыть в браузере (HTML)
go tool cover -html=coverage.out -o coverage.html
```

Проверить:
- Функции без покрытия (coverage: 0.0%) — особенно в `internal/payment`,
  `internal/subscription`, `internal/admin` (финансово-критичные).
- Если покрытие ниже 60% в критичных пакетах — можно ли добавить тесты?
- Строки в обработчиках ошибок, редких условиях — часто они не покрыты.

### 3. Ловушки

**Race detector:** Go может ловить гонки данных, но вывод шумный.

```bash
go test -race ./...
```

Если есть race — это потенциальный баг на продакшене. Нужно чинить.

**Интеграционные тесты:** Если бэк требует БД, Redis, внешних API, тесты могут
падать из-за недостатка окружения. Проверить комментарии в тестах:
- `// +build integration` — запускаются отдельно
- `t.Skip("no database")` — пропускаются, если БД нет

**Timeout:** Некоторые тесты могут зависнуть (бесконечный цикл, deadlock).
Стандартный таймаут `30s` должен ловить такое, но иногда нужен больше.

### 4. Типичные ошибки

- **import cycle** — пакет A импортирует B, B импортирует A. Компилятор такое
  не пустит, но иногда это зелёный флаг пересмотреть архитектуру.

- **undefined reference** — функция/константа не найдена. Обычно опечатка или
  экспорт (имя должно начинаться с большой буквы).

- **nil pointer dereference** — код пытается вызвать метод на nil. Частая причина
  падений. Тест должен это поймать.

- **wrong number of arguments** — функция вызывается с неправильным числом
  аргументов. Компилятор ловит, но иногда значит нужно обновить сигнатуру.

### 5. Контрольный список

- [ ] `go test ./...` прошёл без FAIL
- [ ] Нет таймаутов и панник в stderr
- [ ] Покрытие критичных пакетов >= 60%
- [ ] `go vet ./...` не нашёл подозрительных мест
- [ ] Если есть race detector issues, они явно документированы
- [ ] Новые функции имеют тесты (или добавлены `// TODO: test` комментарии)

### 6. Генерация отчёта

```bash
# Красивый отчёт покрытия с группировкой по пакетам
go test -coverprofile=coverage.out ./... && \
  echo "=== Coverage Report ===" && \
  go tool cover -func=coverage.out | awk '
    NR > 1 { pkg = substr($1, 1, index($1, "/") - 1); if (pkg != prev) { print pkg; prev = pkg } }
    NR > 1 { print "  " $0 }
  '
```

Если что-то упало, в отчёте написать:
- Какой тест упал и почему
- Есть ли race conditions
- Какое покрытие и в каких пакетах его не хватает
- Сорьи ли хардкод для тестирования (моки, моки БД) правильны
