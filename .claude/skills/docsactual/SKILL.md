# Актуализатор документации

Документация устаревает быстро. Пример команды в README может быть неправильный,
пути к файлам в docs могут не совпадать с реальными, ссылки на функции могут
указывать на удалённый код.

## Когда применять

- Добавлена новая фича, нужно описать в docs
- Изменена архитектура (переименованы папки, перемещены файлы)
- Обновлены команды сборки, развёртывания, запуска тестов
- Изменены переменные окружения или конфигурация
- Перед релизом (убедиться, что примеры работают)

## Порядок

### 1. Найти все документы

```bash
# Основные документы
find . -name "README*" -o -name "*.md" | grep -v node_modules | sort

# Типично в проекте:
# - README.md (корневой)
# - docs/
# - .claude/agents/ (есть ли инструкции?)
# - .claude/skills/ (инструкции для скиллов)
```

### 2. Проверить примеры кода и команды

Для каждого `*.md` файла:

**Команды:**
```markdown
```bash
cd web/cabinet && npm run build
```

Проверить:
- Папка `web/cabinet` существует? (`ls -d web/cabinet`)
- Скрипт `build` в `package.json`? (`grep "build" web/cabinet/package.json`)
- Команда запускается без ошибок?
```

**Пути к файлам:**
```markdown
Правка в `internal/api/payment.go`
```

Проверить:
- Файл существует? (`test -f internal/api/payment.go`)
- Если расположение изменилось, обновить ссылку

**Функции и переменные:**
```markdown
Функция `FormatMoney()` определена в `src/lib/format.ts`
```

Проверить:
- Функция на месте? (`grep -n "function FormatMoney\|const FormatMoney" src/lib/format.ts`)

### 3. Проверить структуру проекта

Если docs описывает архитектуру:

```markdown
- `cmd/` — точки входа
- `internal/` — внутренние пакеты
- `web/` — фронтенд
```

Проверить:
- Каждая описанная папка существует
- Если папка переименована, обновить в docs

### 4. Проверить переменные окружения

Если docs упоминает `.env`:

```markdown
TELEGRAM_BOT_TOKEN — токен бота
DATABASE_URL — строка подключения
```

Проверить:
- Переменные используются в коде? (`grep -r "TELEGRAM_BOT_TOKEN" cmd/ internal/`)
- `.env.sample` содержит эти переменные?
- Значения по умолчанию совпадают с docs?

### 5. Проверить версии и зависимости

Если docs упоминает версии:

```markdown
Go 1.21+
Node.js 18+
```

Проверить:
- `go.mod` показывает версию Go
- `package.json` показывает версию Node (в `engines.node`)

### 6. Обновить устаревшие примеры

**Типичные проблемы:**

- Команда изменилась: `npm run dev` → `npm run dev:local`
- Путь переместился: `src/api.js` → `src/lib/api.ts`
- Функция переименована: `getPaymentStatus()` → `getPayment()`
- Переменная окружения переименована: `API_URL` → `VITE_API_URL`

**Как чинить:**

1. Найти все упоминания в docs
2. Проверить реальное состояние в коде
3. Обновить docs
4. Убедиться, что примеры работают

### 7. Проверить ссылки

Если в docs ссылки на другие файлы:

```markdown
[API документация](docs/api.md)
[Установка](./INSTALL.md)
```

Проверить:
- Файлы существуют
- Якоря (if есть) правильные: `[Раздел](#секция)` → есть ли `## Секция`

### 8. Контрольный список

Для каждого документа:

- [ ] Все команды в примерах работают
- [ ] Все пути к файлам верные
- [ ] Все упомянутые функции/переменные существуют
- [ ] Версии и зависимости актуальны
- [ ] Переменные окружения совпадают с кодом
- [ ] Ссылки не ведут в никуда
- [ ] Структура проекта совпадает с реальностью
- [ ] Нет ссылок на удалённые файлы/функции

### 9. Типичные места для проверки

**README.md:**
- Инструкции по установке (npm install, go build)
- Примеры запуска (npm run dev, go run)
- Структура проекта
- Ссылки на другие документы

**docs/ файлы:**
- API документация (пути, параметры, примеры)
- Архитектура (описание папок, пакетов)
- Развёртывание (шаги деплоя, переменные окружения)
- Локализация (какие файлы переводов, как добавить новый язык)

**.claude/skills/ SKILL.md:**
- Команды для запуска (должны быть современными)
- Пути к файлам
- Структура проекта

### 10. Рассказать честно

В ответе писать:
- Какие документы проверены
- Найденные ошибки и устаревший контент
- Что обновлено
- Если документ полностью актуален, сказать "✓ актуально"
- Если что-то не проверилось (нет доступа к команде, сложный случай), объяснить почему

## Notes

- Документация часто отстаёт от кода. Это нормально, если разница небольшая.
- Но примеры кода должны работать: если они не работают, это вводит в
  заблуждение новых разработчиков.
- Если документ поддерживается плохо, лучше удалить его, чем оставлять
  неправильный.
- Большие изменения в docs лучше делать отдельным коммитом "docs: актуализация".
