# Валидатор БД-миграций

Миграция, которая сломала данные на продакшене, откатывается сложно и медленно.
Проверка перед коммитом — самая дешёвая страховка.

## Когда применять

- Любая новая миграция в `db/migrations/`.
- Перед git push, если в коммитах есть `*.sql` в папке миграций.
- Не нужно для правок Go-кода, фронтенда, конфигов.

## Порядок проверки

### 1. Синтаксис и семантика SQL

```bash
cd db && sqlite3 < migrations/NNNN_*.sql --dry-run 2>&1 | head -50
```

Проверить:
- Все SQL-команды завершены точкой с запятой
- Названия таблиц и колонок совпадают с `schema.sql`
- Типы данных существуют (INTEGER, TEXT, REAL, BLOB, NULL)
- Нет опечаток в ключевых словах (CREATE, ALTER, INSERT, UPDATE)

### 2. Потеря и переписывание данных

Миграции могут уничтожить данные молча:

- **DROP TABLE / DROP COLUMN** — потеря всех данных в этой таблице/колонке.
  Проверить: это намерено? Нужна ли резервная копия перед этим? Есть ли
  зависимые таблицы по внешним ключам?

- **DELETE без WHERE** — удаляет ВСЕ строки. Если это не полная очистка
  перед переделкой таблицы, это ошибка.

- **UPDATE SET колонка = значение** без WHERE — переписывает ВСЕ строки.
  Нужна ли здесь WHERE? Тестировалось на тестовых данных?

- **CREATE TABLE IF NOT EXISTS** — если таблица уже есть, команда молча
  игнорируется. Часто это нормально, но иногда нужно ALTER TABLE.

### 3. Блокировки и производительность

SQLite блокирует всю БД при написи, но на большой таблице это может затянуться:

- **Добавление индекса на большую таблицу** — долгая операция. Нормально,
  но нужно знать, сколько это займёт (на продакшене иногда выключают
  индексы во время миграции и перестраивают после).

- **ALTER TABLE на большую таблицу** — SQLite пересоздаёт таблицу целиком.
  На таблице с 10M+ строк это может быть часы. Иногда нужна live-миграция
  (переименование, двойная запись, потом переключение).

- **Внешние ключи в CREATE TABLE** — проверить, что таблицы-ссылки уже
  существуют (иначе миграция упадёт).

### 4. Совместимость с откатом

Каждой миграции нужен откат. Обычно это в отдельном файле downNNNN.sql:

- **DROP TABLE** вверх ↔ **CREATE TABLE** вниз. Данные потеряны, но структура
  восстановлена.

- **ALTER TABLE ADD COLUMN** вверх ↔ **ALTER TABLE DROP COLUMN** вниз.

- **INSERT/UPDATE** для миграции данных нельзя откатить без дампа. Если это
  критичная миграция с потенциалом потери данных, нужна подстраховка
  (резервная колонка, логирование).

Проверить: откат может быть полностью применён? Откат не приведёт к потере
данных, если какая-то миграция после этой уже применена?

### 5. Контрольный список

- [ ] Синтаксис SQL правильный (все `;`)
- [ ] Названия таблиц/колонок совпадают с `schema.sql`
- [ ] Нет случайных DROP/DELETE/UPDATE без WHERE
- [ ] Добавлены индексы, где нужны (для JOIN, WHERE, ORDER BY)
- [ ] Внешние ключи ссылаются на существующие таблицы
- [ ] Откат миграции написан и тестировался
- [ ] На больших таблицах нет блокирующих операций
- [ ] Комментарий в миграции объясняет "зачем" и "почему"

### 6. Рассказать честно

В ответе писать:
- Что именно проверено (синтаксис, данные, индексы, откат)
- Найденные проблемы и как их чинить
- Если миграция невозможна откатить, предупредить
- Если тестирование не сделано, так и сказать
